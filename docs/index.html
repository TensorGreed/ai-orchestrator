Run MCP agents

  • A tool-calling loop: zero, one or many tool calls per step, until the answer or the iteration limit.
  • Supervisor and workers: workers become tools of their Supervisor, each with its own model, tools and memory.
  • Memory per session, and a session tool cache so later turns can reuse full tool output.
  • MCP-native tools over stdio and Streamable HTTP, shortlisted by relevance to the prompt.
  • Agents can stop and ask the user a question mid-run.
  • OpenAI, Anthropic, Gemini, Azure OpenAI, Ollama and OpenAI-compatible models, plus a built-in echo model that needs no key.

MCP control plane

Every MCP server your agents call, in one place.

One MCP registry for every server your agents call, and an MCP gateway that serves their tools to outside clients. L2M probes each server, tracks its tools and what they cost, and enforces who may call what, for agents and clients alike.

  • Registry and onboarding. Health probes, tool schema snapshots with breaking-change diffs, a playground, and import from MCP client config files.
  • Telemetry and policy. Calls, p95 latency, errors, tokens and cost per tool. Allow and deny rules by project, role, server and tool, plus a "no write tools" switch.
  • Gateway. Serve workflows and registered tools to other MCP clients, with per-client tokens and the same policies.
  • Credentials. OAuth 2.1 for remote servers, or each user's own delegated account.
  • Testing. Record MCP calls into cassettes and replay them; l2m mcp check fails CI on breaking changes or blocked tools.
  • Runtime safety. Stdio servers in sandboxed containers, rate limits, concurrency caps and a circuit breaker.

Ship safely

CI for agents.

Treat a prompt or tool change like a code change: replay it against known-good runs before it reaches production.

  • Golden runs and sets. Save good runs, group them, and replay a draft or a saved version against them.
  • Scorers. JSON equality and schema, text similarity, tool sequence, status, budget and an LLM judge.
  • Release gate on publish. A version reaches production only after its replay job passes the gate's policy; an override needs a written reason and is audited.
  • Production capture. Sample real runs with personal data masked, and promote the useful ones into a golden set.
  • A CLI for your pipeline. Run replays, write JUnit results and publish from CI.
ci.sh
# replay the draft against a golden set; non-zero exit when it fails
l2m replay run --set faq-golden --draft --junit replay.xml
# publish a version through the release gate
l2m release publish wf-faq --version 4

Self-hosted foundations

Yours to run. Nothing hosted by us.

L2M is an open-source agent runtime (MIT) that runs only on your infrastructure. There is no hosted edition and no call-home: the product sends no analytics anywhere.

Auth and access

Session sign-in, API keys, TOTP MFA, and SSO through SAML or LDAP (optional packages). Admin, builder, operator and viewer roles, projects and custom roles.

Auth and RBAC →

Encrypted secrets

AES-256-GCM at rest, master-key rotation through export and import, and external managers: HashiCorp Vault built in; AWS, Google Cloud and Azure with their SDK installed. Configs carry secret references, never values.

Secrets →

Signed webhooks

Bearer or HMAC-SHA256 with a replay window and optional idempotency keys, plus signature checks for Stripe, GitHub, Slack, Telegram and Discord triggers.

Secure webhooks →

Schedules and queue

Cron schedules and a database-backed run queue, rate limiting and security headers, and cost tracking with budget caps.

Observability

Prometheus metrics, OpenTelemetry traces over OTLP, request IDs through the logs, and a tamper-evident audit log.

Observability →

Storage and deploy

SQLite by default; Postgres support in progress. Docker images for amd64 and arm64, Docker Compose and a Helm chart.

Everything is optional. A simple workflow runs with no extra configuration. Approvals, release gates, data labels and destinations, production capture and sandboxing stay off until you turn them on.

Get running

From clone to a working MCP agent.

No model key is needed to start: the MCP Agent Quickstart template uses the built-in echo model and an in-process mock MCP server. Swap in real models and servers when you're ready.

Follow the tutorial Try the live demo first
  1. git clone the repository, then pnpm install (Node 20+, pnpm 10+).
  2. Copy .env.example to .env, set SECRET_MASTER_KEY_BASE64 and the bootstrap admin's email and password.
  3. pnpm dev, then sign in at localhost:5173.
  4. Templates → MCP Agent Quickstart → Use template → Run.
