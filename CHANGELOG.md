# Changelog

All notable changes to L2M are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

> **Pre-1.0 note**: until L2M reaches `v1.0.0`, minor version bumps may carry small behavior changes that aren't strictly additive. Breaking changes will always be called out under a "Changed" or "Removed" heading and (for workflow JSON) accompanied by a `schemaVersion` bump.

## [Unreleased]

### Added
- **Argument-aware MCP tool rules.** Tool policy rules can match a call's arguments (`equals`, `one_of`, `starts_with`, `matches`, number comparisons, `between`, `exists`, with dot paths and `[*]`) and the run's data labels, can be limited to workflows or MCP gateway clients, and can take the effect `require_approval`. Precedence is deny, then require approval, then allow. Conditions fail closed: deny and approval rules match when any list item does and treat a missing argument as "not one of", an allow exception needs every item to match; a value no operator can read, a list over 1,000 items, a value past the call's 1 MB of argument text or a spent per-call glob budget matches a deny and never an allow; values compare as trimmed text, number operators read numeric strings, and text operators can ignore case. Agents and MCP Tool nodes pause in the Approvals inbox (one request when "Ask before write tools" also applies), decided by admins; gateway clients get an "approval pending" JSON-RPC error and retry the identical call once within `MCP_GATEWAY_APPROVAL_WINDOW_MS` (optional, 15 minutes) after an admin approves it, are refused for the same window after a rejection, and can have at most 20 requests waiting. Rules can run in **shadow** mode, recorded on every call but never applied. Each call's policy decision is stored with its telemetry row. Migration v47, SQLite and Postgres. With no rules, nothing changes. See [`/docs/product/mcp-tool-policy#conditions`](apps/docs/docs/product/mcp-tool-policy.md#conditions).
- **Safe argument summaries in MCP tool-call telemetry.** Every tool-call row (workflow, gateway and playground calls) keeps an allow-list summary of the call's arguments: booleans, numbers of up to six integer digits, schema enum values and short lower-case tokens outside sensitive keys are kept as they are; repository owners, email domains, URL hosts and path roots (home directories removed) are kept as prefixes; every other value keeps only its shape, length bucket, data classes and a keyed hash (HMAC under a key derived from the master key), so equal values can be compared without being stored. Rows also keep the role, subject source and project the call ran under (migration v48, both stores). On by default; `MCP_TOOL_ARGUMENT_SUMMARIES=false` switches it off. Admins see the summaries on a tool's recent calls. See [`/docs/product/mcp-tool-call-telemetry`](apps/docs/docs/product/mcp-tool-call-telemetry.md).

### Changed
- **Queue jobs and dead-letter entries follow execution history retention.** The history prune now also deletes finished queue jobs (completed or dead) and dead-letter entries older than `EXECUTION_HISTORY_RETENTION_DAYS` (30 days by default), on SQLite and Postgres. Before, they were kept forever. Set `EXECUTION_HISTORY_RETENTION_DAYS=0` to keep everything. Pending and running jobs are never pruned. See [`/docs/operations/queue-and-workers#retention`](apps/docs/docs/operations/queue-and-workers.md#retention).
- **Runtime is now Node 24.** Node 20 reached end of life on 2026-04-30, so the Docker images, CI and docs move to Node 24 (current LTS), and the root `package.json` declares `engines.node >=24` with an `.nvmrc`. Docker users need to do nothing. Running from source needs Node 24. SQLite databases written under Node 20 keep verifying and copying: the legacy audit-text handling is unchanged.

The initial GA release covers production hardening, OSS-growth foundations, and the docs/evangelism flywheel.

### Added

#### Backup, restore and disaster recovery
- **Runbook** — [`/docs/operations/backup-and-recovery`](apps/docs/docs/operations/backup-and-recovery.md): what to back up (the database and, stored apart, `SECRET_MASTER_KEY_BASE64`), SQLite online backup and file copy, `pg_dump`, point-in-time recovery, `db:export` / `db:import`, restore after losing the master key, key rotation, SQLite to Postgres, cluster notes, and RPO / RTO with measured times.
- **Restore drill** — `pnpm dr:drill` (`scripts/dr-drill.mjs`) populates an API through its public endpoints, backs it up with every documented method, restores each backup into a fresh instance and verifies logins (MFA too), secret decryption, data (MCP servers, releases, guard profiles, knowledge bases, pending approvals), the audit chain, the signing key (a run signed after the restore verifies offline) and an agent's sealed write-tool result (the approved write is not run again, also after a key rotation). The **DR drill** workflow runs it on changes to the backup scripts, the database layer, the API's services, the lockfile, the drill or the runbook, weekly and on demand, with Postgres and PITR.
- **`db:export` covers every durable table** — it wrote 29 of 85 tables, so a JSON backup lost MCP servers, approval requests, guard profiles, knowledge bases, releases, audit signing keys and more. Transient tables (caches, leases, replay windows, rate-limit counters, pending challenges) and live sign-in sessions stay out, listed with their reason.
- **`db:import` restores exactly the backup** — it refuses a destination that already holds data (exit 2, nothing written); `--replace` empties every exported table first, including ones an older backup does not hold, and the destination's sign-in sessions, so nothing of the old database is left beside the backup and everyone signs in again (a table that cannot be emptied fails the restore); `--merge` adds rows as before. Each table is logged as restored, emptied (not in the backup) or untouched. It also refuses a backup whose secrets or MFA enrolments `SECRET_MASTER_KEY_BASE64` cannot open (`--allow-key-mismatch` to restore anyway); neither key is printed.
- **`db:import --source-master-key-file <path>`** reads the old key from a file and warns when others can read it. Re-encryption now also re-seals the guard token vault and the approved write-tool results sealed inside paused runs (without that, an approved write could run again after a key change); a value the old key cannot open stops the import with the table's name. A source scan fails the tests when a new place encrypts with the master key.
- **Fixed:** `db:export`, `db:import` and `db:rollback` refused the `--` that `pnpm --filter … <script> -- <args>` passes through.

#### Static live demo at lsquarem.com/demo/

The API client now goes through a small transport seam (`apps/web/src/lib/transport.ts`); in demo mode a Vite plugin points it at an in-browser fake backend, so the demo needs no server and makes no request off its own origin. Normal builds never include demo code or fixtures.

Approving a request says that on a real deployment the paused run would now resume; links straight to the API (exports) show "Not available in the demo". A slim banner and an optional four-step tour come with it.

Deployed by the Pages workflow at `/demo/` (a failed demo build leaves the landing and docs deploying, with a warning); the landing page and docs nav link to it. See `apps/web/demo/README.md`.

#### Audit bundles and signed run manifests
- **Run manifests** — every finished run gets a versioned manifest (`l2m.run-manifest` v1, zod schema in `@ai-orchestrator/shared`): workflow version and hash of the definition as it ran, each node's config with secret references only, model calls with provider, model, parameters, tokens and cost, MCP tool calls with server identity, schema snapshot hash, argument and result digests and outcome (including policy, guard, rate-limit, concurrency and breaker refusals), prompts, citations, approval decisions, totals and a guard verdict summary (`extensions.guard`, no matched content). Canonical JSON (sorted keys) with a SHA-256 digest; generated on first request, stored in `execution_manifests` (migration v29) and never changed afterwards. Runs in progress are refused with 409. `GET /api/executions/:id/manifest`.
- **Signing** — Ed25519 via `node:crypto`. `AUDIT_SIGNING_KEY_BASE64` is used when set; otherwise a key is generated on first use and stored encrypted through SecretService as an internal secret. Key id = first 16 hex of SHA-256(public key). Admins list keys (`GET /api/audit/signing-keys`) and rotate a generated key (`POST /api/audit/signing-keys/rotate`, audited); retired public keys stay listed so older bundles keep verifying (`audit_signing_keys`, migration v29). The private key never reaches responses, logs, manifests or bundles.
- **Audit bundle export** — `GET /api/executions/:id/bundle` streams a zip with the manifest, `signature.json` (signature over an index of every file's SHA-256 and size), the workflow as it ran, node inputs and outputs, trace, logs and rendered outputs, plus a README. Read access to the run's workflow is required; each export is audited as `execution.audit_bundle.export`; `AUDIT_BUNDLE_MAX_BYTES` caps the size (413). A stored manifest is pruned once it is older than `AUDIT_LOG_RETENTION_DAYS` and its execution history is gone. Every secret value the deployment holds (secret store of every project, internal OAuth tokens, cached external secrets, provider keys from the environment) is scrubbed from manifests, JSON and log files and text outputs, including JSON-escaped forms; binary outputs carrying one are left out and listed in the signed `redactions.json`. Audit rows in `logs.jsonl` are limited to the run and carry actor emails only for admin exporters.
- **`l2m audit verify <bundle.zip> [--public-key <file|base64>] [--trust-embedded-key] [--max-bytes <n>] [--json]`** — offline verification: strict zip parsing (no prepended, interleaved or trailing bytes, local headers must match the directory, no case or Unicode-normalisation name collisions, 512 MiB default expansion cap), signature, every file against the signed index, no extra or missing files, manifest digest and run identity, workflow hash. Exit 1 on any failure; exit 3 (SIGNER NOT VERIFIED) when no trusted `--public-key` was given, unless `--trust-embedded-key` is passed.
- **UI** — expanded finished runs on the Runs page show the signed manifest (digest, signing key, signed-at) with an **Audit bundle** download; **Settings → Audit Signing** (admins) shows the key id and public key with copy and download, retired keys and rotation. Documented at [`/docs/security/audit-bundles`](apps/docs/docs/security/audit-bundles.md).

#### External workflow import
- **Converter for exports from another builder** — `convertExternalWorkflow(raw)` in `@ai-orchestrator/workflow-engine` turns an export with top-level `nodes[]`, `connections{}`, `settings` and `pinData` into an L2M workflow plus an import report. Triggers, core nodes and AI nodes (chat models by provider, agents with model / memory / tool attachments, MCP client tools, structured output parsers) are mapped; the common expression subset is translated into `{{results.<id>.x}}` / `vars` syntax with unknown expressions kept verbatim and listed; credentials become `secretRef` placeholders listed by name only; unsupported nodes become disabled `noop_node` placeholders carrying the original config so the flow still loads and validates. Six fixtures with golden outputs live under `samples/external-imports/`. Templates now expose every completed node's output as `results.<nodeId>`.
- **`POST /api/workflows/import/external`** — builder-and-above endpoint that accepts the export as `source` (object) or `sourceText` (string), optional `projectId` / `folderId` / `name`, and `dryRun`. Dry runs return `{ workflow, report }` without persisting; real imports store the workflow with the same validation, versioning and project RBAC as `POST /api/workflows` and record a `workflow.import_external` audit event. Documented at [`/docs/product/importing-from-another-builder`](apps/docs/docs/product/importing-from-another-builder.md), with a coverage table generated by `pnpm --filter @ai-orchestrator/workflow-engine gen:import-coverage`.
- **App node mappings for the external import** — Slack, GitHub, Google Sheets, Postgres, Notion, Jira, Airtable, HubSpot, Salesforce, Stripe, AWS S3, Telegram and Discord nodes are dispatched on their resource/operation pair onto the existing connector and trigger nodes (`packages/workflow-engine/src/import/apps/`). Covered pairs map directly, near misses are approximated with a reason per dropped setting, and other pairs stay disabled placeholders that name the pair. Resource pickers are unwrapped to ids (URLs are parsed), string parameters go through the expression translator, and each app credential becomes a secret placeholder named after what to provide. Four new fixtures (`apps-chat`, `apps-dev`, `apps-data`, `apps-crm-payments`) with golden outputs, and the coverage table gained an "App nodes" section.
- **Import from another builder in the Studio** — a preview-first dialog reachable from Home, the editor's ⋯ menu, the command palette and by dropping a `.json` export on the canvas. It shows the conversion summary and per-node reasons from a dry run before anything is stored. After import a checklist docks on the canvas: link placeholder credentials to stored secrets in one step, fill in variables, rewrite unresolved expressions and replace placeholders, with items ticking off from the live workflow. It also offers Tidy layout and a save-and-validate button. Import JSON now detects these exports and routes them through the same preview. The import report types moved to `@ai-orchestrator/shared` so the web app can use them.

#### MCP server registry
- **Registry of MCP servers** — a new **MCP servers** page and `/api/mcp/servers` endpoints keep every server agents call in one place (`mcp_servers` table, migration v20). Admins register a server once (adapter, connection, auth secret, owner, probe schedule) and MCP Tool nodes or agent `mcpServers` entries reference it with `registryServerId`; the runtime resolves the connection and secret from the registry at run time.
- **Health probes** — the leader instance runs `initialize` + `tools/list` against each server on `MCP_PROBE_INTERVAL_MS` (default 5 min, per-server override, "Probe now" button), recording status, latency p50/p95 and failure rate. stdio probe processes are closed after each probe through a new optional `closeSessions` adapter hook.
- **Tool schema snapshots and diffs** — a snapshot is stored whenever the tool list changes, diffed against the previous one (`diffToolSnapshots` in `@ai-orchestrator/mcp-sdk`). Removed tools or properties, narrowed types, new required inputs and removed enum values count as breaking; servers can block runs until an admin accepts a breaking change. Documented at [`/docs/product/mcp-server-registry`](apps/docs/docs/product/mcp-server-registry.md).
- **Per-tool telemetry** — when a run finishes, every MCP tool call in it is written to `mcp_tool_calls` (migration v21): agent tool calls from `steps[].toolResults` and direct MCP Tool nodes. The agent runtime now records `startedAt` / `durationMs` on each tool result and the provider's `usage` on each step, and agent outputs carry an `_mcpTools` map from exposed tool names back to adapter, tool and registry entry. A turn's tokens are split evenly across the tool calls it requested and priced with the FinOps pricing table (no cost when the model is unpriced). The server page's Tools table shows calls, p50/p95 latency, errors, tokens and cost for the last 24 h, 7 d or 30 d (`GET /api/mcp/servers/:id/telemetry`); usage of servers configured inline on nodes is at `GET /api/mcp/telemetry`. Rows follow `EXECUTION_HISTORY_RETENTION_DAYS`.
- **Tool policy** — admins write allow / deny rules scoped by project, role, server (registry entry, or adapter id for inline servers) and tool name or glob (`mcp_tool_policies`, migration v22; `/api/mcp/policies` routes, `mcp_policy.*` audit events). No matching rule means allowed; deny wins, and an allow rule that sits strictly inside a deny carves an exception out of it. Denied tools are removed before the model sees the tool set (agents, supervisors, workers and attached MCP Tool nodes), every call is re-checked so a call to a hidden tool returns a "blocked by policy" tool error, and direct MCP Tool nodes fail with the rule's name. Runs started by a signed-in user use that user's role; webhooks, schedules, queue workers and other unattended runs use the workflow creator's role (new `workflows.created_by`, backfilled from the earliest version author), falling back to viewer when the creator is unknown or gone. `POST /api/mcp/policies/evaluate` dry-runs a decision, and the **Policies** view on the MCP servers page manages rules and has a "Test a tool" form.
- **Read-only classification and "No write tools"** — the HTTP and stdio adapters keep MCP tool annotations from `tools/list`; snapshots store them only when sent, so existing snapshot hashes are unchanged, and annotation changes are recorded as non-breaking. A tool is read-only when an admin marks it so on the server's Tools table (`PUT /api/mcp/servers/:id/tools/:toolName/classification`), else when its server sends `readOnlyHint: true`; otherwise it counts as a write tool. A workflow's **No write tools** setting (`settings.noWriteTools`, toggled from the editor's ⋯ menu) blocks every write tool. Agent outputs carry `_toolPolicy` with the evaluated role and the hidden tools, shown in the inspector's Trace tab; discovery endpoints mark blocked tools instead of hiding them.
- **MCP gateway: L2M as an MCP server** — `POST /mcp/<toolset>` implements the MCP Streamable HTTP transport (protocol versions 2025-11-25, 2025-06-18 and 2025-03-26; JSON-RPC batches only in 2025-03-26): `initialize`, `ping`, `tools/list` with cursor pagination, `tools/call`, `notifications/cancelled`, and progress notifications over SSE when a request carries a progress token. Sessions use `Mcp-Session-Id` (ended with `DELETE`, closed after `MCP_GATEWAY_SESSION_IDLE_MS`, capped by `MCP_GATEWAY_MAX_SESSIONS`); `GET` returns 405. Requests with a foreign `Origin` get 403 (`MCP_GATEWAY_ALLOWED_ORIGINS`), and CORS on `/mcp/*` follows the same list without credentials. Tool failures are `isError` results; protocol problems are JSON-RPC errors. The legacy `/api/mcp-server/:path/manifest` and `/invoke` routes are unchanged.
- **Toolsets** — `mcp_toolsets` and `mcp_toolset_members` (migration v23) group workflows with an Expose as MCP Tool trigger and registered servers with an optional tool glob; each toolset is served at `/mcp/<slug>`. Workflow tools are named by the trigger's `toolName`; registry tools are re-exposed as `<server-slug>__<tool>` with deterministic slugs, from the server's current snapshot. A gateway call takes the agent's path: registry resolution (blocked on an unaccepted breaking change), secret injection, tool policy (hidden tools are absent from `tools/list` and rejected at call time) and telemetry. Workflow tool calls run the workflow with trigger type `mcp_gateway`, report a progress step per node, and cancel the run on `notifications/cancelled`; stdio servers started for gateway calls belong to the client session and stop when it ends.
- **MCP client credentials** — `mcp_clients` (migration v23) holds per-client tokens (`l2m_mcp_...`, SHA-256 hashed, shown once) scoped to toolsets, with a role, expiry and revocation. Policy evaluates gateway calls as the client's role capped at its creator's current role, with the toolset's project. `mcp_tool_calls` gained `source` (`workflow` | `gateway`) and `client_id`; per-client usage is at `GET /api/mcp/clients/:id/usage`. Audit events `mcp_gateway.*` (session start and end, tool calls with read-only sampling set by `MCP_GATEWAY_AUDIT_READ_ONLY_CALLS`, denials), `mcp_toolset.*` and `mcp_client.*`.
- **Client-side protocol coverage** — the HTTP and stdio adapters now ask for protocol version 2025-06-18, page through `tools/list`, and keep every tool annotation (`title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) and `outputSchema` in snapshots (stored only when sent, so existing snapshot hashes are unchanged). Annotations show as chips on the server's Tools table and in the MCP Tool inspector, and the inspector and an **Outputs** column show output schemas. Output schemas are diffed with the input rules reversed (a removed or widened output property is breaking; an added or narrowed one is not).
- **Structured tool output** — `structuredContent` is validated against the tool's `outputSchema` (missing or non-matching content fails the call with the validation message). MCP Tool node outputs gain `structured` and `content`, so templates can use `{{results.<node>.structured.x}}`; agents get the structured object, plus the text when the text says something else.
- **Progress and cancellation** — tool calls carry a progress token; `notifications/progress` from SSE responses and stdio output reach the run's stream as `node_progress` events, the run tape shows "tool: 40% — message", and node results keep the latest progress. Cancelling a run or hitting a timeout sends `notifications/cancelled` with the request id to every call in flight before sessions close; HTTP requests are then aborted and stdio processes get a short grace period.
- **Annotation conditions in tool policy** — rules gain an optional `annotationHint` (`destructive`, `read_only`, `idempotent`, `open_world` and their `not_` forms; `mcp_tool_policies.annotation_hint`, migration v24), so admins can write rules such as "deny destructive tools for operators". Missing hints follow the MCP defaults, an admin's read-only override applies, and a rule with a condition is narrower than one without.
- **OAuth 2.1 for remote MCP servers** — registry servers with auth type **OAuth** are connected from the server page: 401 challenge → protected resource metadata (RFC 9728) → authorization server metadata (RFC 8414 / OpenID Connect discovery) → dynamic client registration (RFC 7591) unless a client id is configured → authorization code with PKCE S256 and the `resource` parameter (RFC 8707) → `/api/mcp/oauth/callback`. The state is single-use, short-lived (`MCP_OAUTH_STATE_TTL_MS`) and bound to the admin's session and the server. Access tokens refresh before expiry (`MCP_OAUTH_REFRESH_SKEW_MS`) and on 401, with refresh token rotation. Tokens and the client registration are stored only as an internal SecretService secret (hidden from the Secrets list and from node secret references) and are never returned or logged; status lives in `mcp_oauth_connections` (migration v24). The callback URL base is `MCP_OAUTH_REDIRECT_BASE_URL`, falling back to `MCP_GATEWAY_PUBLIC_URL` and then `WEB_ORIGIN`. New endpoints `GET|DELETE /api/mcp/servers/:id/oauth`, `POST .../oauth/connect` and `POST .../oauth/refresh`.
- **Toolsets and Clients views** — the MCP servers page gained **Toolsets** (members, endpoint URL with copy, a preview of the tools each role sees) and **Clients** (create with a one-time token reveal and config snippets for `mcpServers` JSON, `.vscode/mcp.json` and a CLI `add` command; revoke; usage). The `http_mcp` adapter now reports `tools/call` results with `isError: true` as failures. Documented at [`/docs/product/mcp-gateway`](apps/docs/docs/product/mcp-gateway.md).

- **Import MCP client config files** — **Import config** on the MCP servers page (and `POST /api/mcp/servers/import`, admin; builders may `dryRun`) reads `mcpServers` configs (including per-project sections), workspace `servers` + `inputs` files, `mcp.servers` in editor settings, `context_servers` and typed `mcp` maps, with comments and trailing commas allowed. A preview lists every entry with its adapter and connection, a mapped / approximated / skipped report per field, the values that become secrets and the ones still to enter (`${input:…}` placeholders, `${env:…}` references), and matches against registered servers by command and arguments or by URL (skip by default, update or create a copy). Credential-looking env values and headers are stored through SecretService and never appear in connections, responses, logs or audit rows; a server with several credentials gets one JSON **secret bundle** injected by name (`secretEnvVars` / `secretHeaders`, applied by a `withSecretBundle` wrapper on the stdio and http adapters). Imported servers are probed like new registrations; audit event `mcp_server.imported`. Fixtures and golden outputs in `samples/mcp-config-imports/`.
- **Deployment-local MCP catalog** — `MCP_CATALOG_FILE` points at a JSON list of approved servers (id, name, description, adapter, connection template, required secrets, tags, `approved`), validated per entry with zod on start, on change and on `POST /api/mcp/catalog/reload`; local entries must pin their package (`pkg@1.2.3`, `pkg==1.2.3`, `image:1.4.0` / `@sha256:`). A broken file keeps the last good catalog and its errors show on the MCP servers page (`GET /api/mcp/catalog`). `GET /api/mcp/presets` merges approved entries with the built-in presets or, with `MCP_CATALOG_MODE=exclusive`, lists only them. `MCP_CATALOG_ENFORCE=true` limits stdio registrations, edits and imports to approved, pinned catalog packages. Example in `samples/mcp-catalog.example.json`, demo server in `samples/mcp-echo-server/`.
- **MCP playground** — a **Playground** tab (builders and admins) calls any tool of a registered server through a form generated from its input schema (strings, numbers, integers, booleans, enums, arrays of scalars, nested objects, JSON for the rest) via `POST /api/mcp/servers/:id/playground/call`. Calls go through the registry with server-side secret injection, tool policy for the caller's role and active project, a confirmation for write tools, telemetry rows with the new `source` value `playground` and a `mcp_tool.playground_call` audit event. Results show content blocks, structured content, duration and the JSON-RPC exchange with credentials masked; recent calls are kept per user in the browser. Documented at [`/docs/product/mcp-onboarding`](apps/docs/docs/product/mcp-onboarding.md).
- **Resources and prompts** — the HTTP and stdio adapters list and read resources (`resources/list`, `resources/templates/list`, `resources/read`, capped by `MCP_RESOURCE_MAX_BYTES`) and list and render prompts (`prompts/list`, `prompts/get`). Each probe stores what a server advertises in `mcp_server_catalogs` (migration v25), and `notifications/*/list_changed` during a run schedules a debounced re-probe. The Playground gained **Resources** (plain resources, URI templates with per-placeholder inputs, any URI; text, JSON and binary previews) and **Prompts** (arguments, rendered messages) panels. An MCP Tool node's **Operation** can be **Read a resource** (`resourceUri` template; output `text`, `resource`, `contents`), and agent, Supervisor, LLM Call and chat model nodes can bind a server prompt (`serverPrompt`: server, name, arguments, system or user target) that is fetched at run time and recorded as `_serverPrompt`. Tool policy rules gained a **kind** (`tool`, `resource`, `prompt`, `sampling`; `mcp_tool_policies.kind`), evaluated for lists, reads, prompt fetches and sampling; `POST /api/mcp/policies/evaluate` accepts `kind`. New endpoints `GET /api/mcp/servers/:id/resources`, `POST .../resources/read`, `GET .../prompts`, `POST .../prompts/get`; audit events `mcp_resource.read[_denied]`, `mcp_prompt.get[_denied]`.
- **Elicitation** — L2M advertises the `elicitation` capability. When a server asks for input during a tool call, attended runs (editor, Chat, retries, resumed approvals) pause the call and show a schema-driven form in the Chat bubble and under **Waiting for you** on the Runs page; the run stream emits `mcp_elicitation` events. Accept validates against the schema, decline and cancel send only the action; the requester, operators and admins may answer (`mcp_elicitations` table, `GET /api/mcp/elicitations`, `POST /api/mcp/elicitations/:id/answer`). Unattended runs (webhooks, schedules, queue, gateway, public chat widget) and playground calls decline at once with a trace note, credential-looking schemas are refused everywhere, and unanswered requests expire after `MCP_ELICITATION_TIMEOUT_MS` capped by the run timeout. Outcomes are on the node output as `_mcpElicitations` and audited as `mcp_elicitation.*` with field names only.

#### L2M Guard engine
- **`@ai-orchestrator/guard-sdk`** — the Phase 12 guard engine as a standalone library; the workflow engine, agent runtime, API and Studio use it through the guard wiring below. Content on five channels (`prompt`, `model_output`, `tool_arguments`, `tool_result`, `final_output`) with provenance labels, run subject and tool context goes through detectors grouped in latency tiers (`rule`, `parser`, `classifier`, `judge`); `createDefaultGuardRegistry()` returns the built-in ones. Findings carry a category, a 0–1 score, spans, a data class and masked evidence only. Profiles are named, versioned, zod-validated JSON documents with per-channel detectors, thresholds and actions (`allow`, `block`, `redact`, `mask`, `protect`, `transform`, `require_approval`, `review`), per-action shadow mode, a latency budget with `fail_open` or `fail_closed`, a per-data-class protection mapping and a fallback (default `block`); `serializeGuardProfile` / `hashGuardProfile` give a stable serialisation for git sync. `evaluateGuard(profile, input)` runs tiers cheapest first, short-circuits on a non-shadow block, redacts, masks, protects or transforms the content, and returns one verdict with findings, applied actions, timings, budget outcome and a decision trace. Injection findings are never protected, redacted or masked: they block or go to review.
- **Prompt-injection defence, rule tier** — direct and indirect rule packs with weighted patterns and spans (instruction override, role markers, system-prompt extraction, unrestricted personas, known jailbreak personas, safety overrides, text addressing the model, embedded tasks, hidden markup, planted tool calls), matched on the plain text and after leetspeak and base64 decoding; hidden-payload detection for Unicode tag characters, bidi overrides and zero-width runs with a stripping transform; exfiltration detection for markdown and HTML images and links whose URLs carry data and for unexpected outbound URLs in tool arguments; canary tokens; spotlighting helpers (delimiter wrapping, datamarking, prompt-hardening text); a classifier-tier interface with a rule-based stand-in.
- **Tool-argument guards** — SQL guard on an AST per dialect (postgres, mysql, mariadb, sqlite, mssql) classifying read, write and DDL, blocking stacked queries, tautologies, comment tricks and union probes, enforcing table and column allowlists, WHERE on mutations and a row cap (rewrite or check), failing closed on unparseable SQL; command guard for shell metacharacters, substitution, redirection, destructive commands and option-shaped arguments from untrusted input, plus static checks on Python and JavaScript code-node source; path guard resolving against allowed roots with traversal and symlink-escape detection through an injectable `realpath`; egress guard checking URLs against an allowlist after resolution through an injectable DNS resolver and blocking loopback, private, link-local, carrier NAT, cloud metadata, multicast and reserved addresses for IPv4 and IPv6, including IPv4-mapped IPv6 and decimal, octal and hex spellings, hop by hop along a redirect chain; strict JSON Schema validation of arguments (Ajv, undeclared properties rejected) with size and depth limits.
- **DLP and protection** — detectors for email, phone, card numbers (Luhn), IBAN (mod-97), US SSN and a pluggable national-id list, credentials with known key prefixes, JWTs, private-key blocks, high-entropy values next to credential-like names, and custom dictionaries and patterns from the profile; masking helpers; a protection-provider interface (`protect` / `reveal`, deterministic and reversible flags, supported data classes) with `createDefaultProtectionRegistry()` and built-in `mask`, `keyed_hash` (HMAC-SHA-256), `aes_gcm` (AES-256-GCM, reversible) and `token_vault` (reversible, random or deterministic, format-preserving for digits with Luhn-valid card tokens) providers. Keys come through an injected resolver and the vault through an injected storage interface; the package reads no environment variables or files.
- **Benchmark corpus** — `packages/guard-sdk/corpus/` holds labelled direct injection, indirect injection, SQL injection and exfiltration items with benign look-alikes; `benchmark.test.ts` fails when the default profile's detection or false-positive rate regresses past the thresholds documented in `corpus/README.md`. Documented at [`/docs/product/guard-engine`](apps/docs/docs/product/guard-engine.md) with an OWASP Top 10 for LLM applications mapping.
- **Sampling** — L2M advertises the `sampling` capability, off by default per server. Admins turn it on under the server's **Sampling** settings with a token cap, an allowed model list, a per-call request budget and an optional default model (`mcp_servers.sampling_json`). Inside agents and supervisors the attached chat model answers, honouring the server's model hints within the allowed list; direct MCP Tool nodes and gateway calls use the default model or refuse. Each request passes a policy rule of kind `sampling` keyed by model name. Tokens are attributed to the triggering tool call (`mcp_tool_calls.sampling_requests`, `sampling_input_tokens`, `sampling_output_tokens`), rolled into the server's totals and the run's usage, and listed per request under `_mcpSampling` in the inspector's Trace tab. Documented with the risk notes at [`/docs/product/mcp-server-registry`](apps/docs/docs/product/mcp-server-registry.md).
- **MCP control plane** — the single "MCP servers" sidebar item is now an **MCP** section with Overview, Servers, Tools, Policies, Toolsets, Clients, Playground and Changes, each its own page (URL `mode=mcp-*`) and command palette entry; the former tabs keep their behaviour. **Overview** shows servers by status with labels and a table view, pending breaking changes, OAuth connections needing attention, open elicitation questions, servers with sampling enabled, the busiest and most error-prone tools, active gateway clients and the latest changes (`GET /api/mcp/overview`). **Tools** is one catalogue across every registered server with search, filters (server, status, read-only/write, destructive, open world, blocked for my role, has output schema), columns sortable by calls, errors, p95 and cost, and a detail drawer with schemas, annotations, a policy decision for any role and project, recent calls and the workflows that use the tool (`GET /api/mcp/tools`). **Changes** is a chronological feed of schema snapshots and diffs, breaking-change acceptances, status transitions derived from probes, policy and classification edits, toolset and client events, OAuth and sampling changes and resource/prompt lists, filterable by server and kind (`GET /api/mcp/changes`; actors and audit metadata for admins only). On the editor canvas, MCP Tool nodes and tool satellites show the registered server's probe status, a "breaking change" marker and the user's policy state (blocked, destructive, write) that link to the server or the blocking rule, from one cached request per workflow refreshed on focus. Documented at [`/docs/product/mcp-control-plane`](apps/docs/docs/product/mcp-control-plane.md).
- **MCP control plane polish** — tool satellites on the canvas carry larger markers with words ("Blocked", "Breaking", "Write", "2/5 blocked") placed clear of the node; on phones the Tools catalogue shows the server under the tool name, drops p95, cost and the error percentage (still in the drawer) and wraps tool names at `_`, `.`, `-` and `/`; the tool drawer states a block once ("Blocked for you by rule …") instead of repeating the raw policy message; policy errors from runs name the registry server instead of its id.
- **MCP testing: record and replay** — **Record MCP calls** (editor ⋯ menu, eval runs, or `record: true` on `/execute` and `/api/eval/runs`) captures every MCP request a run makes, in order, into a cassette (`mcp_cassettes`, migration v26): lists, tool calls, resource reads, prompt fetches, server capabilities and the sampling and elicitation exchanges of each call, with server identity, schema snapshot hash and timing. Values are scrubbed before they are stored: the server's secret values, credential-looking headers and env, credential-named keys, token-shaped strings and sensitive elicitation answers become `[REDACTED]`, and connections are not stored. Model calls are not recorded. Cassettes are capped by `MCP_CASSETTE_MAX_BYTES` and `MCP_CASSETTE_MAX_CALLS` (marked truncated past either) and follow execution history retention. Recorded runs show a cassette badge on the Runs page that opens a cassette viewer; **Replay** (`POST /api/executions/:id/replay`) runs the execution again against the current workflow with MCP calls answered from the cassette, matched by server, method, name and argument hash. Strict replay (default) never contacts a server and ends the run with an error naming each unmatched call; lenient replay reuses exhausted answers and sends unseen calls to the live server. Eval runs can replay an earlier recorded run fixture by fixture, or one cassette for all. Cassette routes: `GET /api/mcp/cassettes`, `GET|DELETE /api/mcp/cassettes/:id`, `GET /api/mcp/cassettes/:id/export`.
- **Snapshot mock servers** — the `snapshot_mock` adapter serves a registry server's accepted snapshot offline: arguments are validated against each tool's input schema, answers come from a cassette when one is set, else from an example built from the tool's `outputSchema`, else a fixed text. `GET /api/mcp/servers/:id/snapshot/export` downloads the snapshot as a file, and `l2m mcp mock --snapshot <file> [--cassette <file>]` runs the same mock as a stdio MCP server.
- **`l2m` CLI with `l2m mcp check`** — new `packages/cli` (`pnpm l2m …`). `l2m mcp check` calls `POST /api/mcp/check` with an API key: each selected server (all, `--server`, or `--toolset`) is probed without storing anything and diffed against its accepted snapshot, and tools that workflows name are evaluated against tool policy. It exits 1 on breaking changes, unreachable servers (`--allow-unreachable`) and policy-blocked tools (`--allow-policy-blocked`), 2 on usage errors, and prints a summary or `--json`. Offline, `--snapshot <file>` compares a `--stdio` command, a `--url` or another snapshot file. `l2m mcp snapshot export` downloads snapshot files. Documented at [`/docs/product/testing-mcp-workflows`](apps/docs/docs/product/testing-mcp-workflows.md).

- **Sandboxed stdio servers** — a registry stdio server can run in a throwaway container (`sandbox: { mode: "container", image, … }`, admin only) started with docker or podman (`MCP_SANDBOX_RUNTIME`): a pinned image (tag-only images warn, `latest` is refused), CPU, memory and process limits, a read-only root with a tmpfs `/tmp`, a non-root numeric user, all capabilities dropped, `no-new-privileges`, and no network unless turned on. Host folders mount read-only unless marked writable, and only under `MCP_SANDBOX_ALLOWED_MOUNT_ROOTS` after symlinks are resolved, both on save and at start. Secrets reach the container as `--env NAME` without values on the command line. Containers are labelled with their owner process and removed on close, cancel and shutdown; a startup sweep removes only leftovers of this instance's dead processes. `MCP_SANDBOX_DEFAULT` sets the default mode, `MCP_SANDBOX_REQUIRED` refuses unsandboxed stdio servers (inline ones included), catalog entries and imports can carry a `sandbox` block, and `MCP_CATALOG_ENFORCE` still applies. Probes record the sandbox status, shown on the server page and under **Needs attention**.
- **Rate limits, concurrency caps and a circuit breaker** — per registry server (`limits`): calls per minute with burst, concurrent calls, a queue wait, a call timeout, and per-tool rules by name pattern. The breaker opens on consecutive failures or an error rate over a window, refuses calls while open, lets one trial call through when half-open, and counts only transport, protocol and timeout failures. State is per server and per API instance, shared by runs, the gateway and the playground; probes bypass it. Refused calls are a tool error for agents, a failed node without retries, JSON-RPC error `-32029` with a retry hint on the gateway, and a separate `rejection` in telemetry (`mcp_tool_calls.rejection`). Breaker transitions are audited (`mcp_server.breaker_*`), appear in the Changes feed and under **Needs attention**, flag the server list, and mark MCP Tool nodes **Circuit open** on the canvas. `GET /api/mcp/servers/:id/runtime`, `POST /api/mcp/servers/:id/breaker/reset` (admin).
- **Delegated credentials** — an HTTP OAuth server can use each user's own account (`credentialMode: "delegated"`). Users connect under the new **My connections** page (`GET /api/mcp/connections`, `POST /api/mcp/connections/:serverId/connect`, `DELETE /api/mcp/connections/:serverId`); tokens are internal SecretService secrets per server and user (`mcp_user_oauth_connections`, migration v27). A run uses the account of the user who started it, a gateway call uses the client's owner, and unattended runs fail unless `delegatedFallback: "owner"` uses the workflow owner's connection; there is no fallback to a shared credential, and a missing connection fails the node with a link to My connections. Admins list and revoke connections (`GET /api/mcp/servers/:id/connections`, `DELETE /api/mcp/servers/:id/connections/:userId`); the callback only completes for the user who started it. Audit events `mcp_server.user_oauth_*` carry no tokens.

#### L2M Guard in workflows
- **Guard node** — a `guard` node checks one field of the item on a chosen channel with a stored profile or the run's effective profile and routes it to `pass` (with the rewritten field; the parent's unguarded copy is dropped), `blocked` or `review` (to `blocked` when `review` has no edge). `require_approval` pauses the run through the Human Approval flow (`/api/approvals`) with masked evidence; approval sends the item to `pass`, rejection to `blocked`. Any node can now request this hand-off (`ApprovalHandoffSignal`).
- **Agent guard port** — Agent and Supervisor nodes gain a `guard` attachment port (0..1). Its profile checks the prompt, every tool call's arguments, every tool result before the model sees it, and the final answer; a block fails the node (prompt, final answer), withholds the tool call or result with a tool error, a rewrite replaces the content, and review or approval pauses the run and re-runs the node once approved. Workers run their own guard, the Supervisor checks their answers as tool results, and a paused worker pauses its Supervisor. Profiles can turn on spotlighting of tool results with system-prompt hardening and canary tokens. Agent outputs carry a masked `_guard` trace. A port-attached guard node cannot have DAG edges (`guard_port_on_dag`).
- **Stored profiles and bindings** — `guard_profiles`, `guard_profile_versions` and `guard_bindings` (migration v28). Profiles get immutable versions with hash, author and note, a diff between versions, JSON export and import, and field-level validation errors; key material in profile options is refused. The built-in default is seeded read-only. Projects bind a profile as `inherit`, `override` or `enforced` (admins only; builders cannot change it) and workflows as `inherit` or `override`. Agents without a guard port use the enforced profile first, then the workflow or project override, then the built-in default unless `GUARD_AUTO_APPLY=false`; every profile in the stack runs and the most severe action wins. Routes under `/api/guard/profiles`, `/api/guard/bindings`, `/api/guard/effective` and `/api/guard/detectors`; audit events `guard.profile.*` and `guard.binding.updated`.
- **Protection port** — `guard_protection` nodes attach to a guard node's `protection` port (0..N) with `mask`, `keyed_hash`, `aes_gcm` or `token_vault`, a list of data classes, and a key chosen by `keySecretRef` and read through `SecretService` when used. The token vault is stored in `guard_token_vault`, sealed with AES-256-GCM under the master key with a purpose-bound context. With no provider, no key or a failing provider, the profile's fallback applies (block by default). The egress guard now resolves hostnames with the system resolver.
- **Guard events and UI** — every verdict writes `guard_events` rows (channel, detector, category, data class, score, requested and applied action, shadow flag, masked evidence, profile id, version and hash, latency, budget outcome), following execution history retention. `GET /api/executions/:id/guard-events`, `GET /api/guard/events` and `GET /api/guard/stats`. The Runs page shows a Guard panel in each run's trace, the run tape marks guarded steps, a **Security** page shows trends, top detectors, shadow would-blocks and the latest events, and its **Profiles & bindings** tab is the profile editor with the enforced lock. The canvas draws the guard slot on agents, the `pass` / `blocked` / `review` outputs and protection slot on guard cards, and config forms for both nodes. Documented at [`/docs/product/guard`](apps/docs/docs/product/guard.md).

#### Agent runtime depth
- **`agent_clarify` mid-turn pause primitive** — the agent runtime exposes a third built-in tool (alongside `session_cache_list` / `session_cache_get`) that the agent can call when it needs information only the user can provide. Calling `agent_clarify({ question, reason? })` breaks the iteration loop, persists the orphaned tool-call message to session memory, and returns with `stopReason: "clarification_requested"` + a `clarification` field on the result. On the next `run()` with the same `sessionId`, the runtime detects the unanswered tool call and injects the new `userPrompt` as the tool result — so the LLM sees a clean tool-call → tool-result exchange instead of an orphan + a fresh user message. Works at any trigger surface: chat resumes automatically via session memory; webhook / schedule callers inspect `result.clarification` and re-invoke with the reply. New `WorkflowExecutionResult.clarification` top-level field carries `{ question, reason?, toolCallId, nodeId }`. Chat UI renders the bubble with a "?" badge labeled "Assistant is asking" and the optional reason below as italic context. `agent_clarify` tool results are always persisted (overriding the default `persistToolMessages: false`) so subsequent runs don't double-resume. Sample at `samples/workflows/agent-clarify-flow.json`.

#### Phase 9 — RAG depth
- **Built-in persistent knowledge bases** (Phase 9.1) — RAG now works out of the box with no external vector DB. New `knowledge_bases` and `knowledge_base_chunks` tables back a SQLite-only `KnowledgeBaseVectorStoreAdapter` that plugs into the existing `rag_retrieve` node via `vectorStoreId: "knowledge-base"` + `vectorStoreConfig.knowledgeBaseId`. Append-only ingestion, locked vector dimensions, source-id grouping (delete by source), every retrieved document carries `knowledgeBaseId` / `chunkId` / `sourceId` / `similarityScore` provenance. Hand-rolled cosine search in JS — fine up to ~10k chunks per KB; pgvector / Qdrant / Azure AI Search are still available unchanged for larger corpora. New REST endpoints: `/api/knowledge-bases` (CRUD), `/api/knowledge-bases/:id/ingest` (server-side embedding via the KB's configured embedder, or pre-embedded chunks), `/api/knowledge-bases/:id/search` (standalone similarity), `/api/knowledge-bases/:id/sources/:sourceId` (DELETE by source). Migration v18.
- **Document ingestion pipeline + Studio UI** (Phase 9.2) — managing a KB no longer requires `curl`. New top-level **KB** sidebar entry opens a dedicated page: list, create (with embedder picker + JSON config), upload, browse chunks, delete sources, run a test similarity search. New `POST /api/knowledge-bases/:id/upload` chains load → chunk → embed → ingest in one round-trip; loaders cover Plain text, Markdown, HTML (regex-stripped to avoid a cheerio dep), CSV (with optional `textColumn`/`metadataColumns`), and JSON / NDJSON. Chunker is now a shared helper in `@ai-orchestrator/workflow-engine` so the upload endpoint and the existing `document_chunker` workflow node share one implementation. PDF + DOCX intentionally deferred — each needs a binary parser; will land as 9.2.x follow-ups.
- **Citation tracking through the agent chain** (Phase 9.4) — every chunk retrieved by `rag_retrieve` / `hybrid_search` / `rerank` already carries stable provenance from Phase 9.1; this phase turns it into clickable footnotes in the chat UI. New `extract_citations` node resolves `[N]` (or `[chunkId]`) markers in an LLM answer back to the upstream documents and emits structured citations with char offsets, source IDs, similarity / reranker scores, and retrieval mode. `rag_retrieve` and `rerank` now emit a `citationInstructions` string operators can drop into prompt templates so the model knows to cite. Chat bubble renders `[N]` markers as clickable `<sup>` links that scroll to a footnote panel below the bubble (source ID, retrieval mode, score, chunk preview). Backed by a tolerant marker scanner (numeric brackets win on collision; out-of-range markers ignored) and 13 unit + 2 integration tests. Sample at `samples/workflows/rag-with-citations-flow.json`. Also added `rerank` and `extract_citations` to the `WorkflowNodeType` zod schema enum so workflow upserts via REST accept them.
- **Hybrid search + reranker nodes** (Phase 9.3) — built-in KBs now index every chunk in a SQLite FTS5 virtual table at insert time (kept in sync via triggers, no rebuild needed). `rag_retrieve` accepts a new `searchMode: "vector" | "bm25" | "hybrid"` config. `hybrid` fuses BM25 + dense via Reciprocal Rank Fusion (canonical RRF, k=60 default) — catches both keyword-exact matches and semantic paraphrases in one call. New `rerank` node sits after retrieval and reorders candidates via a hosted cross-encoder; three providers wired today (Cohere Rerank v3 / Jina Reranker v2 / Voyage rerank-2). Result metadata propagates `retrieval.mode`, `rrfScore`, `rankers[]` for hybrid hits and `rerankerScore`, `reranker.providerId` after rerank. Migration v19 adds the FTS5 index. Sample at `samples/workflows/rag-hybrid-rerank-flow.json` showcases the canonical retrieve → rerank pipeline.
- **RAG-specific eval scorers** (Phase 9.5) — closes the quality loop on the Phase 7.3 eval framework. Four new `ScorerSpec` variants: `context_precision` and `context_recall` (programmatic, token-overlap with stopword filtering — free, deterministic), plus `faithfulness` and `answer_relevance` (LLM-judge, gated on `EVAL_JUDGE_ENABLED`). Every RAG scorer returns a numeric `score ∈ [0, 1]` (in addition to pass/fail) so dashboards can chart trends, not just counts. Judge plumbing uses the existing provider registry + secret resolution; per-scorer `providerId` / `model` / `threshold` overrides. Settings → Evals run launcher exposes the new scorer types as toggles with cost hints. JSON-tolerant judge response parser handles markdown fences, surrounding prose, and trailing commas so weaker models don't fail loudly on the format.

### Security

- **Rate limiting + security headers** described above directly close gaps from the production-readiness audit.
- **Master-key rotation** is now a first-class operation via the `db:export` / `db:import` CLIs.
- **Verifiable releases** — the release workflow builds each platform of the API and web images on a native runner (arm64 on `ubuntu-24.04-arm`, no QEMU), pushes them by digest and merges them into a multi-arch index (`scripts/release/push-index.sh`), writes a CycloneDX SBOM per platform image (Syft) plus one for the source tree, scans every platform image with Grype (SARIF to code scanning; a fixable CRITICAL finding stops the release), signs the digests with keyless cosign (GitHub OIDC), attests SLSA build provenance (`actions/attest`, also pushed to GHCR) and the SBOMs, verifies all of it, and only then adds the `<tag>` / `latest` tags and attaches the SBOMs, digests and `SHA256SUMS` to the GitHub Release. ## Changelog discipline

Going forward, every PR with user-visible changes adds an entry under `## [Unreleased]` in the appropriate category (`Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`). The PR checklist enforces this for non-trivial changes.

When cutting a release:

1. Move the `[Unreleased]` content under a new heading: `## [vX.Y.Z] — YYYY-MM-DD`.
2. Reset `[Unreleased]` to an empty skeleton.
3. Tag and push: `git tag vX.Y.Z && git push origin vX.Y.Z` — the [release-images workflow](.github/workflows/release-images.yml) builds and publishes container images, and a GitHub Release should be created with the changelog section as its body.

Versioning rule of thumb pre-1.0:
- **Patch** — backwards-compatible bug fixes only.
- **Minor** — new features, behavior tweaks that don't break workflow JSON or env vars. May include schema-additive migrations.
- **Major** — workflow JSON `schemaVersion` bump, env var renames, removed nodes, or any other change a self-hoster has to adapt to. Will not happen before `v1.0.0`.
